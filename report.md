# Restful Booker: результаты тестирования

## Очевидные баги

### BR-001. Отсутствие обязательных полей приводит к HTTP 500

- **Endpoint:** `POST /booking`
- **Кейсы:** `TC-015`–`TC-021`
- **Фактический результат:** при отсутствии `firstname`, `lastname`, `totalprice`, `depositpaid`, `bookingdates`, `checkin` или `checkout` сервис возвращает `500 Internal Server Error` с телом `Internal Server Error`.
- **Ожидаемый результат:** контролируемая клиентская ошибка `400 Bad Request` с описанием невалидного или неполного payload.
- **Оценка:** очевидный дефект обработки входных данных, потому что ошибка клиента не должна приводить к HTTP 500.

### BR-002. Невалидные типы и значения принимаются при создании

- **Endpoint:** `POST /booking`
- **Кейсы:** `TC-022`–`TC-025`
- **Фактический результат:** `totalprice: "100"` преобразуется в число, `depositpaid: "true"` в boolean, отрицательный `totalprice` принимается, дата `01/01/2030` нормализуется в `2030-01-01`; запросы завершаются `200`.
- **Ожидаемый результат:** несоответствующие типы, отрицательная цена и дата вне контрактного формата отклоняются через `400 Bad Request`.
- **Оценка:** очевидный дефект строгой валидации схемы и бизнес-значений. Автоматическое преобразование может скрывать ошибки клиента.

### BR-003. Неверный Content-Type обрабатывается некорректно

- **Endpoints:** `POST /auth`, `POST /booking`
- **Кейсы:** `TC-010`, `TC-028`
- **Фактический результат:** `/auth` с `text/plain` возвращает `200` и `{"reason":"Bad credentials"}`, `/booking` с `text/plain` возвращает `500 Internal Server Error`.
- **Ожидаемый результат:** единообразная контролируемая ошибка `415 Unsupported Media Type` либо `400 Bad Request`.
- **Оценка:** очевидный дефект единообразия обработки media type.

### BR-004. Невалидные query-параметры вызывают HTTP 500

- **Endpoint:** `GET /booking`
- **Кейсы:** `TC-038`, `TC-041`
- **Фактический результат:** `checkin=not-a-date` и повторяющийся `firstname=A&firstname=B` возвращают `500 Internal Server Error`.
- **Ожидаемый результат:** контролируемая ошибка валидации `400 Bad Request` или четко определенное безопасное поведение для повторяющегося параметра.
- **Оценка:** очевидный дефект обработки параметров запроса.

### BR-005. PUT сохраняет невалидный тип как null

- **Endpoint:** `PUT /booking/:id`
- **Кейс:** `TC-053`
- **Фактический результат:** при `totalprice: "x"` сервис возвращает `200`, а в объекте ответа `totalprice` становится `null`.
- **Ожидаемый результат:** запрос отклоняется через `400 Bad Request`; исходные данные не изменяются.
- **Оценка:** очевидный дефект валидации и целостности данных.

### BR-006. GET /ping принимает произвольные query-параметры

- **Endpoint:** `GET /ping`
- **Кейс:** `TC-002`
- **Фактический результат:** `GET /ping?qwe=qwe` возвращает `201 Created` и тело `Created`. Сервис молча игнорирует переданный query-параметр.
- **Ожидаемый результат:** health-check endpoint не должен принимать query-параметры; их следует отклонять (например, `400 Bad Request`) либо явно документировать.
- **Оценка:** несоответствие строгому контракту endpoint'а — лишние параметры принимаются без ошибки и без влияния на ответ.

## Спорные решения API design

Эти особенности не считаются подтвержденными багами без дополнительных требований к контракту:

1. `POST /auth` с неверными credentials возвращает `200` и `{ "reason": "Bad credentials" }` вместо распространенного `401 Unauthorized`. Такое поведение соответствует текущей документации сервиса.
2. `GET /ping` возвращает `201 Created` и текст `Created`, хотя для health-check обычно используют `200 OK`. Поведение задокументировано.
3. Успешный `DELETE /booking/:id` возвращает `201 Created`, хотя семантически чаще используется `204 No Content` или `200 OK`.
4. API автоматически приводит некоторые типы и нормализует даты вместо строгого отклонения входных значений.
5. `GET /booking/1.5` фактически может вернуть `200` и booking object. Для идентификатора обычно ожидается целое число, но отдельный контрактный статус не указан.
6. `PATCH /booking/:id` с `{}` может вернуть `200`, хотя фактически изменения отсутствуют.
7. Неизвестные поля в PATCH могут быть проигнорированы без ошибки, что скрывает опечатки клиента.
8. Период, в котором `checkout` раньше `checkin`, может быть принят. Это потенциальная бизнес-проблема, но явное правило в документации не задано.

## Вопросы для уточнения

1. Должны ли ошибки аутентификации возвращать `401`, или `200` с полем `reason` является обязательной частью контракта?
2. Должен ли API строго проверять JSON-типы без автоматического преобразования строк в числа и boolean?
3. Разрешен ли отрицательный `totalprice`?
4. Какой точный формат дат обязателен: только `YYYY-MM-DD` или допустима нормализация других форматов?
5. Должен ли `checkout` быть строго позже `checkin`?
6. Какой статус должен возвращать `DELETE`: `201`, `200` или `204`?
7. Должен ли дробный `bookingId` отклоняться как невалидный path parameter?
8. Должен ли пустой PATCH отклоняться через `400/422`?
9. Должны ли неизвестные поля отклоняться или игнорироваться?
10. Какой статус ожидается для повторяющегося query-параметра?
11. Должен ли неподдерживаемый `Content-Type` возвращать `415` на всех endpoint'ах?

## Примечание по тестовым данным

- `TC-043` использует гарантированно несуществующий ID `99999999`, поэтому проверка несуществующего ресурса возвращает `404 Not Found`.
- `TC-063` проверяет удаление без авторизации и не отправляет Cookie; на существующем booking сервис возвращает `403 Forbidden`, что соответствует ожидаемой защите.
- `TC-051` и `TC-058` отправляют заведомо невалидный `token=invalid-token`, поэтому проверяют именно отказ при некорректном токене, а не полное отсутствие авторизации.
- Порядок DELETE-кейсов: сначала проверка без авторизации на существующем объекте, затем удаление с валидным токеном, затем повторное удаление и удаление несуществующего ID.
